Intel Arc B580 firmware debugging — part 2 (opromdata & VBT dissection)

Continuing from the GSC recovery — investigating the remaining GuC idle crash and PCODE instability through opromdata analysis.

The GSC reflash got the card online, but two problems persisted. PCODE was still intermittently failing on cold boot, and a GuC idle crash loop was occurring roughly 90 seconds after the desktop loaded regardless of workload — guc_exec_queue_timedout_job, seqno=213, in no process [-1].

Narrowing the remaining problem

The Windows golden image recovery tool (IntelGFXFwUpdateTool v6.0.36) had previously flashed fwcode and opromcode back to golden image versions, but explicitly skipped fwdata as incompatible. opromdata was never touched by any tool on either OS.

Research confirmed via fwupd GitHub issue #9889 that opromdata and fwdata are 4-ID matched — specific to the board partner's subsystem vendor and device IDs. The ASRock Challenger B580 carries subsystem ID 1849:6021. Solaris17's Arc-Firmware repo lists this card as "Unknown Version" with no matching opromdata available. The card was running a generic reference opromdata never intended for the Challenger's physical hardware.

Working hypothesis: GuC reads power state transition tables from opromdata during init. A mismatch between those tables and what the ASRock hardware actually expects causes GuC to time out waiting for a transition that never completes. The subsequent dirty shutdown corrupts card state, causing PCODE to fail on the next cold boot. The two symptoms are one chain, not two independent problems.

Obtaining the reference opromdata

The file bmg_e20b_1100_config19.bin was pulled from Solaris17's repo — the generic e20b opromdata, the closest publicly available equivalent to what the Challenger should have. The file is 65,536 bytes (64KB).

Binary structure

The file has two distinct layers.

The first 2,048 bytes (0x0000 to 0x07FF) form an Intel Code Partition Directory ($CPD) manifest. This region contains an OROM.man manifest entry, a VBT entry (1,344 bytes), and VBT.met metadata (1,220 bytes). A $MN2 Intel manifest header at 0x338 indicates this region carries an RSA signature blob. If the platform verifies this signature at flash time, any patch to this region would be rejected.

The remaining 63,488 bytes (0x0800 to 0xFFFF) form a standard PCI Option ROM, beginning with the 55 AA signature at 0x0800 and a PCIR data structure at 0x081C identifying vendor 0x8086 (Intel). This is the patchable region.

VBT structure

The Video BIOS Table header sits at absolute offset 0x283C with the signature $VBT BATTLEMAGE. Key header fields:

  • Version: 100
  • Total VBT size: 7,287 bytes (ends at 0x44B3)
  • Checksum byte: 0xF7 at absolute offset 0x2856 — must be recomputed after any patch
  • BDB offset from VBT start: 0x0030, placing the BIOS Data Block header at 0x286C

The BDB header signature confirms BIOS_DATA_BLOCK, version 257.

Blocks of interest for patching

Block 27 (panel/pipe timings, 814 bytes) contains repeating 20-byte groups with values consistent with power state timing parameters: 0x07D0 (2000), 0x000A (10), 0x01F4 (500), 0x1388 (5000). These are the most likely source of the GuC idle timeout — if the Challenger's hardware expects different transition timing, GuC would stall waiting for a state change that never arrives within the expected window.

Block 10 (Child Device Table, 203 bytes) is entirely zeroed except for the entry size byte. A fully empty child device table means no port assignments are hardcoded, which is unusual for a shipping card and may contribute to display topology confusion at init.

Block 58 (Driver Features, 674 bytes) controls capability flags including PSR, DC states, and GuC submission configuration.

Block 56 (HDMI Level Shift, 210 bytes) is almost entirely zeroed after the first byte (0x0d), suggesting HDMI transmitter level configuration is not populated in this reference build.

GSC verification question

The critical unknown before any patch can be flashed is whether the GSC validates opromdata content at write time. The $CPD manifest region contains what appears to be an RSA signature. If the GSC checks this on opromdata writes the same way it does for fwcode, a patched binary would be rejected regardless of content correctness.

Evidence suggesting opromdata may be less strictly validated: igsc can read opromdata back from the card via /dev/mei1 without issue, and the 4-ID matching system exists precisely to allow board partners to customise this region post-fabrication — which would be impractical under mandatory per-board RSA signing.

The CH341A physical flash programmer is the definitive next step. Dumping the chip from another ASRock B580 Challenger will answer two questions at once: what the correct VBT content looks like for this specific hardware, and whether the $CPD signature region differs between ASRock's version and the Solaris17 reference. If the signature bytes are identical, flashing a patched binary via igsc is viable. If they differ, a different approach is needed.
